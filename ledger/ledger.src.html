How to read this record

Limits of this record: it is not a verbatim transcript. It reconstructs each request, the decision taken, the reason, how it was checked and what it left open. Entries

E01Nov 6

“Create a game like Steal a Brainrot (Roblox) but for celebrities, as a YouTube Playables game. Bots instead of players, bots steal from the player and the player steals from bots. Make it 3D, like you're uploading it to go viral, following YouTube rules.”

Did
Built “Star Heist” from scratch: game/index.html (HUD, title screen, shop), game/game.js (all logic), three.js copied in locally so nothing loads from the internet. World: a moving red carpet where celebs spawn every 2.0–2.9 s; six agencies (the player's plus five bots: RoboRich, Glitchy Gus, Cyber Sue, Botzilla, MegaByte); 8 podiums each; celebs earn cash per second into their podium; the player collects by walking past. Steal loop: grab a celeb from a bot podium, carry it home slower, the owner chases and a touch returns it. Defence: a laser door lock (step on a pad) and a camera “Flash” that stuns bots in a radius. Six rarity tiers, Gold/Diamond/Rainbow mutations (x2/x3/x5), Star Storm and Golden Hour events, five upgrades, a four-step tutorial with a pointer arrow, offline earnings (25 %, capped at 2 h), leaderboard, minimap, procedural WebAudio music and sound. Characters are blocky people built from boxes; each limb group is merged into one mesh with vertex colours to keep draw calls low on phones.
Why
Real celebrities were never used: names or likenesses of real people would breach right-of-publicity law and YouTube review. The Playables SDK calls (first frame, game ready, load/save, audio, pause/resume, score) were wired through a wrapper that falls back to localStorage outside YouTube. The flash is a soft glow, not a strobe, for photosensitivity.
Checked
Playwright screenshots; a 10-minute simulated match. Found bots were absurdly rich (~700 K vs the player's 4 K), so bot income was cut to 0.4x and their allowance lowered.
Result
Preview artifact published; upload zip ~205 KB; LAUNCH_KIT.md with store copy and a compliance table.
Open
The SDK function names (ytgame.game.firstFrameReady and so on, script URL youtube.com/game_api/v1) came from memory, not from reading YouTube's docs in this session. They have never run inside real YouTube.

Process mistakes the builder made

  • Removed the wrong thing first when asked about “panels” (E11) before diagnosing properly.
  • Two shell commands containing inline scripts were blocked by a safety check; nothing ran, and both were rewritten as files.
  • One commit step failed because a copy command used the wrong folder; the device check had passed and the commit was re-run.
  • A test script had its own bugs (desktop tap on a touch API, too little cash for the tap test) that briefly looked like game failures.
  • Answered “push to GitHub” four times when nothing was pending, instead of noticing the user may have expected something else to happen.

Claims the critic should attack first

  1. That the game would pass YouTube Playables certification. It has never run inside YouTube, and the SDK names are from memory.
  2. That the iPad problem is fixed. No WebKit or real-device test exists.
  3. That the economy is balanced. No simulation of a real player's progression from zero to prestige was ever run.
  4. That the memory check passing means there is no leak.
  5. That the ?debug test hook is harmless in production. Anyone can append ?debug and get full control of the save.
  6. That the GOAT-based content (rebirths 8–10, three fusion recipes, prestige) is reachable at all.
